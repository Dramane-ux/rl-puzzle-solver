# RL Puzzle Solver

Interactive web application where reinforcement-learning agents learn to solve a
**3×3×3 Rubik's Cube** and a **Pyraminx** (regular tetrahedron, "tipless" variant).
Built for the *Stochastic Processes* module (M2IA). The interface is in French;
code, comments and this README are in English.

The whole project models each puzzle as an explicit **Markov Decision Process**
(states, actions, stochastic transitions, reward, discount) and compares three
solvers:

| Agent | Idea |
| --- | --- |
| **Q-learning** | Tabular temporal-difference learning with ε-greedy exploration |
| **Double Q-learning** | Two value tables to remove the max operator's overestimation bias |
| **MDP (value iteration)** | Breadth-first state graph + exact value iteration |

## Pages

- **Accueil** (`/`) — hero with the short problem statement and the two entries

- **Simulateur** (`/simulateur`) — pick a puzzle, then the `cube` / `pyraminx`

## Modelling

- **States** — one colour configuration. Cube: 54 stickers; Pyraminx: 36 stickers
  (4 triangular faces × 9 triangles), exactly 933 120 states.
- **Actions** — cube: 12 quarter turns `[U, U', D, D', L, L', R, R', F, F', B, B']`;
  Pyraminx: 8 vertex rotations (4 vertices × {+120°, −120°}, `U, U', L, L', R, R',
  B, B'`), stored in inverse pairs.
- **Transitions** — deterministic rotation, except with probability `p` (slip) a
  uniformly random action is executed instead. The process is therefore genuinely
  stochastic.
- **Reward** — `-1` per move, `0` at the solved (absorbing) state; discount `γ`.
- **Learning taps** — pessimistic initialisation, retrospective replay of each
  scramble backwards, and a self-paced curriculum that only raises the scramble
  depth once the success rate exceeds 95 % (measured at the current level).
- **Planning** — for the Pyraminx, a bounded look-ahead (horizon `k`, default 4)
  runs on the learned Q-table at solve time, extending the reach to the full
  diameter without retraining.

Default hyper-parameters: `α = 0.5`, `γ = 0.95`, `p = 0.05`, `init = −15`,
`maxStates = 1 000 000`. Per puzzle: cube `maxDepth = 5`, `ε: 0.3 → 0.15`,
episode length `3·d + 6`; Pyraminx `maxDepth = 8`, `ε: 0.2 → 0.2`, episode length
`1·d + 3`, planning horizon `k = 4`, `maxEpisodes = 3 000 000`.

## YuXin HuangLong 5×5 Pyraminx (Tiled)

The rounded-tetrahedron choice has been replaced by the YuXin HuangLong 5×5 Pyraminx:
100 triangular stickers, 24 corner-layer rotations, a tiled exterior, bulged faces and
rounded tips. The puzzle mechanics are generated by `buildTetrahedron(5)` in
`src/engine/tetrahedron.ts`; the rounded shape is a display-only deformation, so the
engine state and move permutations remain unchanged.

- **Q-learning and Double Q-learning** are trained to depth 3.
- **MDP** is bounded to depth 4.
- **Planning** uses a bounded look-ahead horizon of 2.

The measured results are loaded from `src/data/tetra5-results.json` and displayed on the
Résultats page.

## Measured results

Produced by `npm run benchmark` (seed 12345, 80 trials per cell) and written to
`reports/`. These numbers are quoted in the written report; the website no
longer embeds them — nothing is hard-coded:

| Puzzle | Depth | Q-learning | Double Q | MDP |
| --- | --- | --- | --- | --- |
| Cube 3×3×3 | 4 | 100 % | 100 % | 100 % |
| Cube 3×3×3 | 5 | 59 % | 61 % | 100 % |
| Pyraminx | 8 | 95 % | 93 % | 100 % |

The Pyraminx state space has exactly **933 120 states** and a diameter of **11
moves**; the MDP enumerates the whole graph and converges in ≈ 26 value
iterations. Q/DQ alone are reliable up to depth 8; the bounded planner (horizon
`k = 4`) then reaches the full diameter (8 + 4 ≥ 11).

**Fundamental limit.** The 3×3×3 cube has ≈ 4.33·10¹⁹ states, so tabular
Q-learning is reliable only up to **4 moves**; beyond that the table grows faster
than the memory cap. The Pyraminx is finite (933 120 states), so it is solved
completely — Q-learning up to depth 8 and the bounded planner beyond. The app
states all this explicitly. Deep Q-Networks are mentioned only in the written
report, and are **not** implemented.

## How it works in the browser

Training runs inside a **Web Worker** (`src/agents/worker.ts`) so the interface
never blocks. The main thread talks to it through `SolverClient`
(`src/agents/client.ts`) using a small request/response protocol. The main
thread owns the puzzle animation (Three.js for the cube and the Pyraminx) and
replays the solution returned by the worker.

## Benchmark CLI

```bash
npm run benchmark
npm run benchmark -- --max-depth 6 --trials 100
```

By default the measurements are written to `reports/` (not used by the website):

- `reports/results.json`
- `reports/benchmark.csv`
- `reports/robustness.csv`

Flags: `--puzzles`, `--algorithms`, `--depths`, `--max-depth`, `--trials`,
`--episodes`, `--max-states`, `--seed`, `--out`. The CSV files are written next
to the JSON file.
